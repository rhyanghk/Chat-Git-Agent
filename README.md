# Chat-Git-Agent

这是一套让“聊天端负责安排、执行端负责做事、项目文件负责记住结果”的协作规则。

目标只有三个：

1. 换聊天、换电脑、换执行工具后，仍能从项目文件继续；
2. 任务是谁做、做什么、不能做什么、怎么判断完成，都有明确记录；
3. 远端仓库只负责同步和保留版本，没有远端仓库也能工作。

## 三条安装边界

### 1. 聊天端只安装聊天规则

把 `聊天端/CHAT_CORE.md` 加到聊天项目的数据源，并让聊天项目始终按它工作。

聊天端负责：理解你的要求、第一次接入项目时建立 `.ai/`、整理项目现状、创建任务、选择执行角色、给执行端生成最短启动提示、验收结果、更新长期记录。

### 2. 执行端只安装执行规则

把 `执行端/` 整个目录复制到执行工具长期可读取的用户目录。

执行端负责：读取通用规则、自己的角色规则、聊天端给出的启动提示和项目任务文件，然后在本地执行；完成后把结果写回项目的 `.ai/reports/`。

### 3. 业务项目零预装

一个普通业务项目第一次接入前，不需要放任何本项目文件。

聊天端第一次接入后，才在业务项目里建立：

```text
.ai/
├─ INDEX.md
├─ context/
│  ├─ PROJECT.md
│  ├─ ARCHITECTURE.md
│  ├─ MEMORY.md
│  └─ DECISIONS.md
├─ tasks/
│  ├─ ACTIVE.md
│  └─ TASK-xxxx.md
├─ reports/
└─ handoff/
   └─ CURRENT.md
```

`reports/` 在第一份结果出现时再建立，不为了目录完整创建空文件。

业务项目里不放聊天端通用规则、执行端通用规则、角色规则、安装说明。

## 不用 GitHub 也能完成全部工作

最简单的本地流程：

```text
你提出要求
↓
聊天端读取本地项目并更新 .ai/
↓
聊天端给执行端启动提示
↓
执行端在本地项目里工作
↓
执行端写 .ai/reports/...
↓
聊天端读取结果和实际改动
↓
接受、继续修改或再做一次独立检查
```

如果使用 GitHub，只多两件事：执行前先把远端内容同步到本地；执行完成后按任务授权把本地提交同步回远端。GitHub 不负责决定任务，也不是项目能否工作的前提。

## 一次任务怎么走

1. 你把目标和不能碰的边界告诉聊天端。
2. 聊天端创建或修改 `.ai/tasks/TASK-xxxx.md`。
3. 聊天端选择一个执行角色。
4. 聊天端生成很短的启动提示，只告诉执行端去哪里读规则、任务和结果写到哪里。
5. 执行端只做这一个任务，完成后写结果文件。
6. 聊天端对照任务、实际文件改动和验证结果验收。
7. 只有以后仍然有用的内容，才进入项目长期记录。
8. 合并、发布、接受重大风险等决定仍由人做。

## 从哪里开始

- 安装聊天端：`聊天端/安装.md`
- 安装执行端：`执行端/安装.md`
- 第一次接入业务项目：`项目接入/第一次接入.md`
- 日常使用：`使用.md`
- 检查整套规则是否完整：`检查清单.md`
- 跟随原项目更新：`维护/跟随原项目更新.md`

## 更新方式

本项目不会复制原项目的目录和说法，而是保存一张“原文件 → 本项目规则”的对应表。以后原项目有新提交时，只检查真正会改变行为的内容，再用本项目的简单说法吸收。

本项目当前核对原项目到：

```text
youling/ai-use@1ddfeb0dd6a606dbc80ab86de8903d6888077bc6
```

详见 `维护/跟随原项目更新.md` 和 `维护/对应表.md`。
